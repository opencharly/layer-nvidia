# 2026.295.1958 — feat(nvidia): add the nvidia-cdi-host CDI host layer

## Summary

Adds the `nvidia-cdi-host` layer to `opencharly/layer-nvidia` — the W4/C2 implementation of `CONTAINERD-IMAGES.md` §1.5, extending the existing `nvidia` candy (tracked in #16).

- **Handler.** `nvidia-ctk runtime configure --runtime=containerd` with an explicit, layer-owned `--drop-in-config /etc/containerd/conf.d/99-nvidia.toml`; **no `--enable-cdi`** (CDI is always on in containerd 2.x and the key is ignored with a warning) and **no `--set-as-default`**. The step fails closed if the handler or the `imports` entry does not land.
- **Live, not merely written.** Restarts `containerd` after the drop-in. containerd reads its config at startup, so a drop-in written while the daemon runs is not served: measured on a scratch daemon, `0` nvidia runtimes after the write and `2` after a restart.
- **Durable spec.** Enables **and starts** `nvidia-cdi-refresh.path` and `.service`, so `/var/run/cdi/nvidia.yaml` is regenerated at boot, on module load and when the toolkit changes, and exists on a fresh host before the checks run. No one-shot `cdi generate --output=/etc/cdi/nvidia.yaml`.
- **Rootless.** One link helper resolves the user's `$XDG_CONFIG_HOME` (default `~/.config`) and links `cdi/nvidia.yaml -> /var/run/cdi/nvidia.yaml`. A `user-tmpfiles.d` rule covers a user that does not exist at build time, at the client default `%h/.config` (systemd-tmpfiles has no `XDG_CONFIG_HOME` specifier — its documented limitation).
- **Device-gated checks.** `nvidia-ctk cdi list` reports `nvidia.com/gpu=all`, `crictl info` serves the `nvidia` handler, `--device nvidia.com/gpu=all` runs `nvidia-smi -L`, and the rootless client resolves the same device. The exit code is never the gate: `cdi list` exits 0 on an invalid spec.
- **Bed.** `check-nvidia-cdi-host` carries the three-step absence / perform / presence shape, rootful **and** rootless, each daemon on its own scratch root/state/socket. The absence baseline starts from an unrelated `imports` entry, so the perform step must prove `nvidia-ctk` adds the drop-in directory; the deployed step asserts the already-running host daemon.

Arch/omarchy only. A Fedora arm is additive and is not claimed until its own disposable bed exists (CONTAINERD-IMAGES §1). `distro-cachyos#151` (the one-shot form in `candy/nvidia-driver`) remains its own fix and is deliberately not copied here.

This round also fixes every finding of the first BLOCK: the missing containerd restart, the not-started refresh units, the XDG_CONFIG_HOME handling, the inconsistent no-user branch, the bed's pre-seeded `imports` baseline, and the over-claimed end-to-end bed evidence (now stated as the remaining gate).
