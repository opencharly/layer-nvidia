# 2026.323.1906 — fix(nvidia): walk the nvidia/vdpau/xorg trees from the one layout list

## Summary

Three states are in play, and they are different code:

- **A — the issue's tree (9f073ea).** The delete loop walked `/usr/lib /usr/lib64`;
  the tree removal named ONLY `/usr/lib`; the residue count walked
  `/usr/lib /usr/lib64`; the predicate was the over-broad `libcuda*.so*`.
- **B — this branch's base (`origin/main`, 9f073ea's successor).** The delete and the
  residue count already walk `libs` (`/usr/lib /usr/lib32 /usr/lib64`, #27); the
  tree removal still names ONE `/usr/lib` path, and the xorg assertion still reads
  the literal `/usr/lib/xorg/...`.
- **C — this PR.** The tree removal AND the xorg assertion walk the same `libs`
  list as the baseline, the delete and the residue count; the list is overridable
  (`NVIDIA_STRIP_LIB_DIRS`) so the step can be executed against a fixture.

So B could already remove `/usr/lib32`'s driver FILES (via `libs`) while still
leaving `/usr/lib32`'s and a real `/usr/lib64`'s TREES — and B's xorg assertion read
the HOST's literal `/usr/lib/xorg/...`, which the fixture caught on its first run.
The `drv=` predicate is untouched: `diff` against the producer's five-line block
(`layer-cuda` `v2026.323.1604`) is empty.
