# 2026.320.1938 — fix(arch): stop baking the driver user-space, which shadowed the CDI-injected host libs

## Summary

**Successor to opencharly/layer-nvidia#21**, which the validator auto-closed at its
5-verdict threshold. Every finding from those five rounds is fixed in this tree (they are
itemised in the round RCA carried over at the bottom of this thread's predecessor), so this is
the same change on a clean branch and thread — not a narrower one. The paired
opencharly/layer-cuda#19 is **MERGED** (`v2026.320.1929`).

This candy's own skill has always stated the rule: *"Driver userspace libraries
(libcuda, libnvidia-ml, etc.) are NOT bundled — CDI provides host-matching driver libs at
runtime, preventing version mismatches between container and host kernel module."* The
Fedora arm obeyed it. The Arch arm did not: `nvidia-utils` installs the whole driver
user-space (89 files under `/usr/lib`), and NVIDIA's CDI `create-symlinks` hook points
each SONAME at the **newest** versioned copy present INSIDE the container — so the image's
copy beat the injected host copy, and on a host whose kernel driver is older than the
distro's package, NVML fails:

```
$ nvidia-smi -L                      # cachyos ollama image, host driver 615.78.08
Failed to initialize NVML: Driver/library version mismatch
NVML library version: 620.70        (exit 18)
$ ls -l /usr/lib/libnvidia-ml.so*
/usr/lib/libnvidia-ml.so.1 -> libnvidia-ml.so.620.70.06     # baked by nvidia-utils
/usr/lib/libnvidia-ml.so.615.78.08                          # mounted by CDI
```

CUDA kept working (the injected `libcuda` is what runs), so the breakage was confined to
NVML: `nvidia-smi`, and every Vulkan/EGL consumer on a skewed host. It is also why
`check-cachyos-ollama-pod`'s `ollama-gpu-visible` step has been red for ANY ollama pin —
measured on the pre-bump candy too.

Three changes, in this order inside the plan:

1. **`nvidia-drop-driver-userspace`** removes exactly the set the CDI spec injects
   (`libnvidia-*`, `libcuda*`, `libnvcuvid`, `libnvoptix`, `libGLX/EGL/GLESv*_nvidia`,
   plus the `/usr/lib/nvidia`, `/usr/lib/vdpau` and `nvidia_drv.so` trees). The package
   STAYS installed: it also owns assets that are not host-coupled and that this candy uses
   — the Vulkan ICD JSON the wiring step links, and `nvidia-smi`.
2. **That same `run:` asserts its own result** — it prints how many driver libraries are
   still baked and fails the build if the count is not zero. The enforcement lives here,
   not in a `check:` step, for a measured reason: a `check:` step runs in a container the
   GPU seam may attach, where the host's libs sit at the SAME paths, so telling baked from
   injected needs `/proc/self/mountinfo` — which is not readable on every venue (that
   probe went red on a CORRECT fedora image). The `run:` executes in the build container,
   where nothing has been injected, so a remaining match is unambiguously image content.
3. **`nvidia-distro-runtime-assets`** replaces the old *"the nvidia userspace for THIS
   distro is present, either the Arch driver libs from nvidia-utils or …"* check, which
   asserted precisely the opposite: it listed `/usr/lib/libnvidia*` and required `nvidia`
   in the output. It went red on a correct image the moment the strip landed
   (`stdout: expected to contain "nvidia" (got: )`). It now asserts what a composed image
   must actually have: the Vulkan ICD JSON (Arch), the VA-API driver (Fedora), and
   `nvidia-smi`.

Three candidate probes were measured before the enforcement design above was chosen:
presence-only (red on a correct GPU-attached image), version-versus-loaded-module (red —
several driver libs carry their own soname version, e.g. `libnvidia-egl-gbm.so.1.1.3`),
and `st_dev` (red — the image store and the host share one btrfs here). Only "runs in the
build container, where nothing was injected" is sound.

The skill page (`/charly-distros:nvidia-layer`) is updated in the same PR with the
mechanism, the measurements, and why the enforcement sits in the `run:`.

## Change classification

**Breaking change + rollback:** this is the one consumer-visible change in the pair — the
Arch/CachyOS images stop carrying driver user-space, so at run time the driver libraries
come from the CDI mount. Every GPU seam in charly is CDI-based, so nothing in the org
loses capability (CUDA, NVML, Vulkan, OpenCL all resolve through the injection, at the
host's matching version — which is the fix). A consumer that ran one of these images
WITHOUT CDI would lose the driver libraries entirely; none exists, and that is the
documented contract rather than an incident. Rollback is reverting this commit and
opencharly/layer-cuda#19 together: either alone leaves the invariant half-enforced, and the
build-time assertion will say so.

Change class: **Candy config** — static `charly box validate`, live `check-ollama-pod`
(Fedora, no regression) and `check-cachyos-ollama-pod` (the targeted Arch arm).
